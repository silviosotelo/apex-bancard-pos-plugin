apex-bancard-pos-plugin

POS Bancard – Cobro directo (cliente)

Oracle APEX Dynamic Action plugin: charge a physical Bancard POS terminal directly from the cashier's browser, with no application server in between. Framework-agnostic, drop into any APEX app.

Oracle APEX 20.2 / 22.x / 24.x Dynamic Action plugin MIT License
github.com/silviosotelo/apex-bancard-pos-plugin

1Why it exists, and how it works

A server-to-server integration with a Bancard POS terminal only works if the application server can reach the terminal's local IP over the network. In a lot of real deployments the app server and the terminal sit on different network segments, and that path never connects.

This plugin is the alternative path: the machine that is on the same LAN as the terminal is the cashier's browser, not the server. The plugin does a direct fetch() from the browser to the terminal's local IP/port — no backend in between.

Coexists, doesn't replace. Built to work alongside an existing server-to-server integration, if you have one: use that path where the server can reach the POS, use this plugin where it can't. Both can live on the same page.

Execution flow

  1. The cashier triggers the Dynamic Action (e.g. clicking a "Charge with POS" button).
  2. The plugin's JavaScript does POST /pos/eco to the terminal (5s timeout) to confirm it's awake.
  3. Depending on the configured Medio de Pago, it calls the matching terminal endpoint (90s timeout) — card, QR, e-wallet, etc.
  4. Writes the terminal's raw result into the configured destination items.
  5. All feedback —loading, success, error— shown with SweetAlert2, bundled with the plugin (no CDN dependency).

No round-trip to an application server in between: the entire Bancard protocol runs in the browser. The reference number (facturaNro) is generated with Date.now(), no database sequence involved.

Feedback: SweetAlert2 modal, always

Technical note — why the loader doesn't use Swal.showLoading(). That SweetAlert2 method works by converting the "Confirm" button into the spinner; if there's no visible button to convert (showConfirmButton:false), the spinner has nowhere to render. And if the swap isn't reverted cleanly before the next alert, the "Confirm" button can stay hidden forever. Instead, the plugin builds the spinner by hand in the modal's html (reusing the .swal2-loader CSS class already in the bundle) with showConfirmButton:false fixed: there's never a button during loading, and never anything to revert.
Mandatory browser requirement (real terminal only). The Bancard terminal speaks plain HTTP and doesn't send CORS headers. If your app is served over HTTPS, the browser blocks the fetch() unless, once per cashier machine: (1) chrome://flags/#block-insecure-private-network-requests is disabled, and (2) an "Allow CORS"-type extension is installed and enabled. Not needed against the bundled simulator (section 5): it already answers proper CORS headers.

2Installation

Recommended: through the APEX UI

Shared Components → Plug-ins → Create Plugin, filling in the fields by hand:

  1. Identification: Name BANCARD.POS_CLIENTE, Display Name "POS Bancard - Cobro directo (cliente)", Type Dynamic Action, Category JavaScript.
  2. Source → PL/SQL Code: the render function (full code in install/manual_ui_install.md).
  3. Callbacks → Render Function Name: render.
  4. Settings: API Version 1, Supported UI Types Desktop, Substitute Attributes = Yes.
  5. Files: upload js/pos_bancard_cliente_bundle.js (SweetAlert2 + plugin runtime, single file — two separate files in JavaScript File URLs render as one broken <script> tag).
  6. Custom Attributes: the 11 attributes listed in section 3, all Attribute Scope = Component, Type = Page Item.

Full step-by-step with exact copy-paste field values: install/manual_ui_install.md.

Why not just run the SQL script? The install/*.sql scripts use wwv_flow_api.create_plugin/create_plugin_attribute with manually chosen IDs. In practice, a hand-picked ID can end up as a literal small number instead of a real APEX-generated ID (every other plugin in a real app has a 15-20 digit ID). A small ID can collide with something else in the instance's internal ID space, and since plugin metadata loads application-wide (not per-page), a single bad ID can break Page Designer for an entire application. Installing through the UI avoids this entirely — it's the same code path Oracle uses to generate every other plugin's ID.

Installing into another app / workspace

Once installed anywhere, the standard APEX way to move it: Shared Components → Plug-ins → open the plugin → Export, then in the target app Shared Components → Plug-ins → Import File. APEX resolves the target workspace/app/owner automatically and generates a real ID.

3Integrating it into a charge/payment page

The pattern that works end-to-end has three pieces in the same Dynamic Action:

Why piece 3 is a separate event, not a third chained action. The plugin's action runs asynchronously without telling the Dynamic Action engine to wait — as far as APEX is concerned, it "finishes" as soon as it's triggered, not when the POS responds. A chained action right after it would run immediately, before any result exists. The plugin does not suppress the change event on its destination items, so a separate Change-triggered action on one of them always fires once a result is actually in.

Piece 1 — example PL/SQL

Bind variables, not apex_application.g_x01. "Execute Server-side Code" reads/writes items with :ITEM_NAME directly, via "Items to Submit"/"Items to Return" — it doesn't wait for or print JSON with sys.htp.p. That other pattern belongs to a page-level Ajax Callback process invoked from JavaScript via apex.server.process(...) — a different mechanism, different syntax. Mixing them means the action silently sets nothing. 
declare
  l_ip_pos     my_terminals_table.ip_pos%type;
  l_puerto_pos my_terminals_table.puerto_pos%type;
begin
  select t.ip_pos, t.puerto_pos into l_ip_pos, l_puerto_pos
    from my_terminals_table t
   where t.branch_id = :P_BRANCH_ID
     and t.register   = :P_REGISTER
     and t.active      = 'Y';

  :P_POS_IP     := l_ip_pos;
  :P_POS_PUERTO := to_char(l_puerto_pos);
  :P_POS_MEDIO_PAGO := case :P_CARD_TYPE
                          when 'DEBIT' then 'TARJETA_DEBITO'
                          else 'TARJETA_CONTADO'
                        end;
  :P_POS_MONTO_PLANO := trim(replace(:P_AMOUNT, '.', ''));
exception
  when no_data_found then
    raise_application_error(-20001, 'No POS terminal configured for this register.');
end;

Piece 3 — example result mapping

function formatThousands(n) {
  n = Math.round(Number(n) || 0);
  return n.toString().replace(/\B(?=(\d{3})+(?!\d))/g, '.');
}
apex.item("MY_RECEIPT_NUMBER_ITEM").setValue(
  formatThousands(apex.item("P_POS_NRO_BOLETA").getValue())
);
apex.item("MY_AMOUNT_ITEM").setValue(
  formatThousands(apex.item("P_POS_MONTO_COBRADO").getValue())
);

Downstream mapping (each app's own responsibility)

Each company keeps its own card-brand catalog (issuerId → internal brand id). The plugin doesn't know it; the mapping happens in the page, typically in the same "Change" event from piece 3:

var myBrand = MY_BRAND_CATALOG[ apex.item('P_POS_ISSUER_ID').getValue() ] || 99;
apex.item('MY_CARD_BRAND_ITEM').setValue(myBrand);

// Same applies to date formatting: convert P_POS_FECHA (ISO 8601)
// to whatever format your save process expects.
This is intentionally each app's responsibility, not the plugin's — it's what lets the same, unmodified plugin be installed in any application, with its own brand catalog and its own save format.

5Testing without a physical terminal

simulator/pos_simulator.py implements all 13 real Bancard v1.5.0 endpoints, runs on the same machine or over the LAN, no external dependencies:

python pos_simulator.py --port 3000

Simulating realism: delay and random outcomes

FlagWhat it does
--delay-cliente N or N-MSimulates how long the customer takes to complete the transaction. Fixed value or random range (different every sale). Applies to everything except /pos/eco.
--randomInstead of always approving, randomly rejects sales (insufficient funds, expired/blocked card, etc.), times out, or fails /pos/eco itself.
--fail-rateRejection probability (0-1). Default 0.15.
--timeout-rateTimeout probability (0-1). Default 0.03.
--eco-fail-rateProbability the /pos/eco check fails. Default 0.05.
--interactiveApprove/reject/timeout each sale from the console instead, to reproduce a specific case.
python pos_simulator.py --port 3000 --delay-cliente 5-10 --random
Mind the gap between simulated delay and the plugin's timeout. The plugin's operation timeout is 90 seconds. If --delay-cliente's max is close to or above that, the browser can report Failed to fetch instead of completing the test — keep the delay range comfortably below the timeout.

Full endpoint/flag reference: simulator/README.md. To try the plugin alone, no APEX app needed: js/demo.html.

6Troubleshooting

SymptomLikely cause
Failed to fetch against a real terminalMissing chrome://flags + "Allow CORS" extension setup on that machine.
Failed to fetch against the simulator--delay-cliente too close to the plugin's 90s timeout — lower the delay range.
"POS did not respond in time"Terminal off, wrong IP/port, disconnected cable, or (against the simulator) --random rolled a timeout.
Configuration items arrive empty at the plugin's action"Execute Server-side Code" (piece 1) written with g_x01/sys.htp.p instead of bind variables — see section 3. No error thrown, just sets nothing.
Plugin action chained after another async action never gets its attributesMove the result mapping to a separate "Change" event (piece 3), not a chained action — see section 3.
Charge button doesn't show/hide live as the form changesA server-side button condition only evaluates at page render — add your own show/hide Dynamic Action bound to the relevant items.
Page Designer breaks app-wide (can't open any Dynamic Action, any page)A plugin installed with a manually-typed small ID via wwv_flow_api — see the danger box in section 2. Uninstall with WWV_FLOW_API.REMOVE_PLUGIN and reinstall through the UI.

7APEX version compatibility

Built and tested on APEX 20.2. The API this plugin's render function uses is stable and documented from APEX 20.1 onward:

  • The apex_plugin.t_dynamic_action / t_dynamic_action_render_result API is stable and documented. Comparing the official definitions for 20.1 against 24.2, the 15 attribute_01..attribute_15 fields this plugin uses didn't change; 24.2 only adds new fields at the end this plugin doesn't need.
  • SweetAlert2 ships bundled as the plugin's own file, not loaded from an external CDN — a strict Content Security Policy script-src would block a <script> pointing at an external CDN domain not explicitly allow-listed.
  • APEX 24.1 deprecated "Substitute Attribute Values" for region plugins; doesn't affect this plugin, which uses the simpler, stable Dynamic Action pattern (p_render_function only).
Installing through the UI (section 2, recommended path), version compatibility is handled by APEX itself — doesn't depend on any hand-typed p_release. The install/*.sql scripts remain in the repo mainly as a readable reference for the plugin's source code.
